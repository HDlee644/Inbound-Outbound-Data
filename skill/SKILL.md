# Reconciliation Review Tool Builder

This skill captures a working pattern developed over a real multi-round build: a monthly goods-receiving reconciliation tool for a food company's purchasing/logistics team. That tool went through several rounds of real user feedback (schema guesses that were wrong, a security model that had to be explained honestly, a design that got rejected twice before landing). The point of this skill is to skip straight to the version that survived that feedback, then adapt it to whatever the new domain is — not to re-derive it from scratch and repeat the same mistakes.

**Start from `assets/template.html`, don't write from zero.** It's a complete, tested, working tool (originally "월별 입고내역 검토 도구" — monthly inbound-goods review tool). Copy it to the target project location, then customize labels, column synonyms, the matching key, and tolerance rules for the new domain. Regenerating the whole thing from a blank file throws away real fixes (see "Hard-won lessons" below) and they tend to get silently reintroduced.

## What this tool does, structurally

Two datasets come in as Excel/CSV uploads:
- **기초자료 (base/master data)** — the authoritative record, one file, covers everyone (e.g. all vendors' inbound receipts for the month).
- **업체별 자료 (counterparty-submitted data)** — one or more files, each representing what the other side (vendor, branch, supplier) says happened.

The tool matches rows between the two by a composite key, computes quantity/amount differences, and marks each matched row pass/fail against tolerance thresholds. Rows present on only one side are automatically a fail ("업체자료 누락" / "기초자료 누락"). Results roll up into a per-counterparty summary, a fail-detail table, an optional month-over-month comparison (by re-uploading last month's own generated output), and a downloadable Excel workbook.

## Build workflow

1. **Find out what the two datasets actually look like before building anything.** Don't guess real-world column names (ERP exports vary company to company). If the user hasn't attached sample files, ask what columns exist, or just build the column-mapping step (already in the template) and let the first real upload drive it — but don't skip straight past this to writing matching logic against assumed field names.
2. **Confirm the matching key and tolerance model.** Default good answer: item code + counterparty name + date, with an admin-adjustable % tolerance for quantity and for amount, plus a free-form custom-rule builder (field/operator/threshold/label) for anything else admin wants to flag. Ask what "pass" vs "fail" should mean for this domain specifically — don't assume 0% tolerance is right.
3. **Confirm whether month-over-month comparison matters.** If yes, the pattern is: the tool's own exported Excel includes a summary sheet in a stable, well-known column format, and next period the user re-uploads that same file as "previous period data" — no separate storage needed, no server.
4. **Confirm whether admin/user view separation is wanted**, and if so, whether some people need read access to detail without full admin rights (the template's answer: a hamburger-menu-driven view switch, plus an admin-issued name+access-code tier for read-only detail access — see `references/permissions.md`).
5. **Confirm whether photo/document evidence attachment matters** (e.g. damage photos, delivery photos). If yes, attach it to the specific counterparty-file entry, not a generic global upload area — see `references/photos-and-export.md` for why and how.
6. Copy `assets/template.html` to the project, then customize: page title, field synonyms in `FIELD_DEFS`, the matching key in `makeKey()`, default tolerance values, section labels, and the reconciliation domain's terminology throughout (검토 대상월 → whatever period unit applies, 업체 → whatever the counterparty is called, etc.).
7. **Test it before handing it off.** Use a browser tool to build two tiny synthetic Excel files in-memory (via SheetJS `XLSX.utils.json_to_sheet` + `XLSX.write`), feed them through the actual upload inputs via `DataTransfer`, run the review, and check the results render with no console errors — this is the single most reliable way to catch a broken matching-key assumption or a mapping bug before the user ever touches it. See `references/testing-pattern.md` for the exact scripted approach that worked (including a known false-positive: `computer{action:"screenshot"}` can time out or return a stale/blank frame when the preview pane isn't focused — that's a tool quirk, not a bug, so confirm via `read_page`/`get_page_text`/console checks instead of trusting a blank screenshot).
8. If the user later asks to share it (e.g. on GitHub), that's a separate, generic concern — not part of this skill. Point them at ordinary git/GitHub steps: scope the repo to just the tool's folder (not a parent folder that might contain unrelated files), `.gitignore` the tool's own generated output files (result `.xlsx`/`.zip`), and if they want a no-download live link, GitHub Pages works directly since the tool is static HTML with CDN dependencies.

## Hard-won lessons (why the template looks the way it does)

- **Column mapping UI, not hardcoded field names.** The first version guessed Korean ERP column names directly and would have silently produced wrong matches against a real file. The fix: parse whatever headers are actually in the uploaded file, best-guess a mapping via a synonym list, but always show the mapping in an editable form and remember the confirmed mapping (`localStorage`) so it's a one-time step per file shape, not a recurring chore.
- **Two views, one file — not two separate files.** It's tempting to ship an `admin.html` and a `user.html`. Don't: `file://` origins in Chromium-based browsers are isolated per exact file path, so two files can't share `localStorage`, meaning rules/mappings/user lists set up by the admin would silently not exist on the "user" file even on the same PC. The working answer is one file with a `currentView` state (`'admin' | 'user'`) driving `body[data-view=...]` CSS visibility, switched via a hamburger-triggered nav drawer.
- **PIN/access-code gating is a screen-privacy convenience, not security — say so, in the UI copy itself, not just in chat.** Anyone who can open the file can read the PIN check in devtools. This is fine for "don't let a coworker glance at vendor pricing on a shared screen," not fine as the only protection for actually sensitive data. The template's admin-note text already says this; keep saying it when customizing.
- **Photos attach to the specific counterparty-file entry**, each upload box gets its own small photo dropzone (see `buildVendorPhotoUI` in the template), not one global "attach evidence" area disconconnected from which submission it's evidence for. Export mirrors this: a ZIP with one subfolder per counterparty.
- **Design went through three rounds before landing**: neumorphism (looked soft but the user found it low-contrast and dated), then a bare flat/bordered style (technically fine but read as "no design at all" — too sparse), then the current one: white cards on a light-gray page, a thin gradient accent bar, colored icon badges per section (a different tint per section so sections are visually distinguishable at a glance), hover-lift on cards/buttons, and a slide-in sidebar drawer (not a tiny dropdown) for navigation. If asked to reskin, treat the current state as the good default, not neumorphism — that direction was explicitly tried and rejected.
- **Client-side only, CDN-only.** SheetJS (`xlsx.full.min.js`) for reading/writing Excel, JSZip for bundling Excel+photos into one download. No build step, no server — it has to keep working as a single file someone double-clicks, or as a GitHub Pages static site. Pin CDN versions (don't use `latest`).
- **Diff columns and grouped table headers matter more than they seem.** Early feedback specifically flagged that showing base-value and counterparty-value side by side without a diff column forces the reader to do mental arithmetic — add an explicit diff column (color-coded), and group "기초/업체/차이" under a shared "수량"/"금액" header spanning three sub-columns. Right-align all numeric columns.
- **Screenshots of the tool during testing can come back blank even when the DOM is correct** if the preview pane isn't frontmost/focused — verify via computed styles / `getBoundingClientRect` / `get_page_text` / console errors before concluding something is actually broken.

## Reference files

- `references/data-model.md` — the exact matching/aggregation algorithm (composite key, aggregation, tolerance comparison, custom rule evaluation) with the working code shape, so you can adapt field names without breaking the logic.
- `references/permissions.md` — the admin/user view-switch and access-code system in full: data model, PIN setup flow, per-user access codes, access log, and the honest caveats to keep telling the user.
- `references/photos-and-export.md` — per-counterparty photo attachment, Excel workbook sheet layout, and the ZIP bundling code (JSZip) for shipping Excel+photos together.
- `references/testing-pattern.md` — the exact in-browser synthetic-data test recipe (build fake xlsx via SheetJS in memory, inject via `DataTransfer`, run, assert on DOM/console) used to verify the tool actually works before handing it to the user.
- `assets/template.html` — the full working reference implementation. Copy and customize; don't rewrite from scratch.
